# План миграции RAG: TF-IDF → Dense Embeddings

> **Статус:** предложение, НЕ исполняется без отдельного «да».
> **Охват:** замена ретривера `src/rag/retriever.py` (sklearn TF-IDF + FAISS + RU→EN
> translation) на dense-embedding retrieval. Часть инициативы «довести всё по красоте»
> (backend-часть, продолжение Flutter↔FastAPI wiring).

---

## 1. Текущее состояние (что меняем)

- `src/rag/retriever.py`:
  - Векторизация чанков: **sklearn `TfidfVectorizer`** (8000 признаков, n-gram 1–2,
    EN+R Uтокены), L2-normalize → `faiss.IndexFlatIP`.
  - Запрос: RU→EN перевод через `RU_EN_TERMS`, затем TF-IDF + keyword boost.
  - Индекс: **~12 024 чанка**, локально в `knowledge_base/`, fallback на HF Hub
    (`shrayyyy/vet-derm-rag`).
- Источники: 17 JSON-файлов `assets/data/*` + `advanced/*`.
- Потребители индекса: Gradio `app.py` (`rag_search`, `dose_calculate`), FastAPI
  `src/api/app.py` (`/v1/rag/search`, `/v1/chat/completions` с `use_rag`).

### Почему TF-IDF всё ещё жив
- Работает **без API-ключа и без сети** (полностью локально / на HF Space CPU).
- Дёшево: индекс строится за секунды, не нужны квоты эмбеддинг-моделей.
- Для узкоспециализированной ветеринарной дерматологии keyword-match + RU→EN
  зачастую достаточен.

---

## 2. Зачем мигрировать (и почему не сейчас)

| Выгода embeddings | Риск / стоимость |
|---|---|
| Лучше ловит **семантику** (синонимы, перефраз, опечатки), которую TF-IDF пропускает | Реиндекс **~12k чанков** через embedding API = квота + время (возможно 10–60 мин при лимитах) |
| Меньше зависимости от ручного `RU_EN_TERMS` (можно мультиязычную модель) | Новая зависимость: эмбеддинг-эндпоинт (Z.AI / sentence-transformers) — **точка отказа в проде** |
| Единый векторный поиск вместо гибрида | Регрессия качества, если модель плохо покрывает вет.-термины (нужен A/B) |
| Проще масштабировать базу | Индекс не строится на лету — нужен отдельный build-шаг / CI-артeфакт |

**Вывод:** миграция оправдана только если A/B покажет заметный прирост и мы
гарантируем offline-fallback. Без явного «да» — не трогаем.

---

## 3. Предлагаемый подход — гибрид, не «выключить старое»

Не удаляем TF-IDF. Добавляем **dense-retrieval поверх**, объединяем через
Reciprocal Rank Fusion (RRF):

```
final_score = α · rrf(tfidf_rank) + (1-α) · rrf(embedding_rank)
```

- `α` подбирается на валидационном сете (стартуем с 0.5).
- Если эмбеддинг-сервис недоступен → `α=1` (чистый TF-IDF), приложение не падает.

### Кандидаты на embedding-модель
- **Z.AI embeddings** (`api.z.ai/api/paas/v4` — как у GLM, единый шлюз) — минимум
  новых зависимостей, но надо проверить наличие и лимиты embeddings-эндпоинта.
- **sentence-transformers** (`paraphrase-multilingual-mpnet-base-v2`) — локально,
  мультиязычно (RU+EN), не нужен ключ, но ~400MB модель + CPU-инференс на HF Space
  (медленнее при холодном старте). Лучший кандидат для offline-first философии VetEco.
- **bge-m3** — мультиязычный, сильный, но тяжелее.

## 4. План работ (поэтапно, каждый этап — отдельный PR)

### Этап 0 — Заморозка бейзлайна (обязательно)
- Собрать **gold-сет запросов** (≥50 реальных RU-запросов ветврачей + ожидаемый
  релевантный чанк/документ). Хранить в `src/rag/eval/gold_queries.jsonl`.
- Скрипт `src/rag/eval/baseline.py`: прогоняет TF-IDF, считает Recall@5 / MRR.
  Это «полка», ниже которой падать нельзя.

### Этап 1 — Прототип эмбеддинг-ретривера (isolated, ветка `feat/embeddings`)
- Новый модуль `src/rag/embed_retriever.py` (не трогаем `retriever.py`).
- Функция `build_index()` — один раз генерит `knowledge_base/embeddings.faiss` +
  `embeddings_meta.json` (чанки, id). Запуск локально / в CI, не в рантайме запроса.
- Функция `search(query, top_k)` — эмбеддит запрос, `faiss.IndexFlatIP`, возвращает
  ранжированные чанки.

### Этап 2 — A/B валидация (блокирующая)
- `src/rag/eval/compare.py`: гибрид (RRF) vs TF-IDF vs pure-embeddings на gold-сете.
- **Критерий перехода:** гибрид не хуже TF-IDF по Recall@5 И показывает прирост MRR
  ≥ +5% (или равно при меньшем числе «промахов»). Иначе — откат, оставляем TF-IDF.

### Этап 3 — Интеграция за флагом
- `src/settings.py`: `RAG_MODE = "tfidf" | "hybrid" | "embedding"` (default `tfidf`).
- `app.py` / `src/api/app.py`: выбор ретривера по флагу. `use_rag` в `/v1/chat/completions`
  не меняет контракт.
- Flutter-клиент **не трогаем** — он общается с API, детали retrieval его не касаются.

### Этап 4 — Offline-гарантия
- Если `RAG_MODE != "tfidf"` и эмбеддинг-сервис недоступен → авто-fallback на TF-IDF,
  лог warning. UI/клиент этого не замечает.

### Этап 5 — Документация и build-шаг
- Добавить `make build-rag-index` (или CI job), который пересобирает оба индекса при
  изменении `assets/data/*`. Без свежего индекса прод не стартует в `hybrid`/`embedding`.

## 5. Риски и митигация

| Риск | Митигация |
|---|---|
| Эмбеддинг-квота исчерпана → RAG «слепой» | Авто-fallback на TF-IDF (Этап 4) |
| Модель плохо понимает вет.-латынь/сокращения | Оставить RU→EN translation-слой ПЕРЕД эмбеддингом запроса; A/B до свопа |
| Реиндекс 12k чанков дорог при каждом деплое | Индекс — артефакт CI, не строится в рантайме; кэш на HF |
| Регрессия в проде после свопа | Флаг `RAG_MODE` + мгновенный откат на `tfidf` без редеплоя кода |
| Увеличение размера HF Space (модель/idxfiles) | sentence-transformers модель ~400MB — проверить лимиты Space; иначе Z.AI API |

---

## 6. Что НЕ делаем
- Не удаляем `RU_EN_TERMS` и TF-IDF до успешного A/B.
- Не меняем Flutter-клиент (он за API-контрактом).
- Не запускаем реиндекс в рантайме запроса.
- Не мигрируем, пока нет gold-сета и baseline-метрик (Этап 0).
